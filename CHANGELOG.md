# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Added

- Inventory ship application contract (INV-04): internal `shipForOrder({ orderId, actor }, tx?)` ships the full ACTIVE reservation set for one order (`onHand -= qty`, `reserved -= qty`, `ACTIVE → SHIPPED`, `SHIP` ledger) in one PostgreSQL transaction with order-scoped advisory serialization, all-or-nothing multi-SKU behavior, all-`SHIPPED` idempotent replay, ship vs release winner semantics, joinable opaque `TransactionContext`, and displayable Persian ship-conflict messages. No ship HTTP, Orders module, partial fulfillment, Redis locks, or returns.
- Inventory reservation and release application contracts (INV-03): `reserveForOrder` / `releaseForOrder` with collapsed multi-SKU lines, all-or-nothing availability inspection, deterministic `productId` locking, `orderId` idempotency (identical replay / mismatched or partial/terminal conflict), order-scoped PostgreSQL advisory serialization, `releaseForOrder` ACTIVE→RELEASED with all-RELEASED replay, joinable opaque `TransactionContext` for future Orders, and displayable Persian shortage/conflict messages. No reservation HTTP, Orders module, SHIP, Redis locks, or reservation TTL.
- Admin inventory warehouse commands (INV-02): `POST /api/v1/admin/inventory/:productId/receive` and `POST /api/v1/admin/inventory/:productId/adjust` (signed delta + required reason) with UUID `Idempotency-Key` replay/conflict semantics, `GET /api/v1/admin/inventory/:productId`, `InventoryCommandIdempotency` persistence, Persian displayable error messages, atomic balance+ledger+idempotency transactions via `AdminInventoryOperationsService`, and `INVENTORY_READ` / `INVENTORY_ADJUST` authorization. No write-off HTTP, reservation/release orchestration, or inventory list pagination (INV-06).
- Inventory persistence primitives (INV-01B): `Inventory`, `InventoryReservation`, and append-only `InventoryLedger` with database CHECKs (`onHand`/`reserved` non-negative and `reserved <= onHand`), Product 0/0 backfill and create-time `ensureForProduct`, atomic conditional PostgreSQL quantity updates, reservation ACTIVE→RELEASED/SHIPPED transitions, partial unique order-lifecycle ledger idempotency, and an opaque `TransactionContext` for modular-monolith composition. No Inventory HTTP, Orders, Redis stock, or workers.
- Inventory architecture (INV-01A): accepted ADR 0012 for PostgreSQL-authoritative `onHand`/`reserved`, derived `available`, reserve-at-create / ship-at-`SHIPPED` lifecycle, append-only ledger, atomic conditional updates, and Orders↔Inventory contracts; durable policy in `instructions/inventory.md`. Schema/persistence remains INV-01B.
- Admin Media Library (CAT-04): reusable `Media` metadata (no PostgreSQL binaries); S3-compatible `StorageProvider` with in-memory test/dev adapter (forbidden in production); Admin `POST /api/v1/admin/media/upload` (`files` multipart, single or batch) with independent per-file results and HTTP 200 on mixed outcomes; `GET /api/v1/admin/media`, `GET /api/v1/admin/media/:id`, `DELETE /api/v1/admin/media/:id` gated by `MEDIA_READ` / `MEDIA_MANAGE`; JPEG/PNG/WebP magic-byte validation; bounded batch/size/concurrency; derived public URLs; ADR 0011; `instructions/media.md`. Product/Blog attachment, SVG/GIF, private ACL, and orphan reconciliation remain later work. Live object-storage credentials were not used in this environment.
- Product catalog and integer-Toman price representation (CAT-03): Prisma `Product` (`id`, trimmed `name`, `price` int4 Toman with positive CHECK, `categoryId` FK `ON DELETE RESTRICT`, `isActive`, timestamps) with additive migration; public paginated `GET /api/v1/products` and `GET /api/v1/products/:id` (active product + active Category only); Admin `GET/POST/PATCH /api/v1/admin/products` (+ detail) gated by `CATALOG_READ` / `CATALOG_MANAGE`; CAT-01 list/search/sort/filter; no inventory quantities, SKU, description, or media FK (MED-01 / MIG-01 / INV-01); ADR 0010; `instructions/catalog.md` Product boundaries. Current price mutation will integrate with PriceHistory in PRC-01; Orders must snapshot title/price (ORD-01).
- Category and Region reference models and APIs (CAT-02): Prisma `Category` / `Region` tables (`id`, trimmed `name`, `isActive`, timestamps) with additive migration; public `GET /api/v1/categories` and `GET /api/v1/regions` (active-only full lists); Admin list/create/update under `/api/v1/admin/categories` and `/api/v1/admin/regions` gated by `CATALOG_READ` / `CATALOG_MANAGE`; CAT-01 Admin list query support; deactivation preferred over hard delete; `instructions/catalog.md`; OpenAPI operations `Categories_*`, `Regions_*`, `AdminCategories_*`, `AdminRegions_*`. No Product/Inventory coupling; name uniqueness, slug, and hierarchy deferred pending MIG-01 evidence.
- List, pagination, search, filter, and sort primitives (CAT-01): reusable `src/common/list` query/response helpers with strict `page`/`pageSize` validation (defaults 1/20, max pageSize 100, no silent clamping), optional trimmed `search`, resource-owned `createSortQueryDto` allowlists with default sorting, explicit filter composition via Nest query DTOs, strict unknown-query rejection, safe integer/boolean query parsers, date-range naming convention, Prisma-neutral `PageRequest`/`toPaginatedResponse` helpers, OpenAPI `createPaginatedResponseDto`, and `instructions/list-queries.md`. No business resources and no generic CRUD framework.
- Admin authentication runtime (ADM-AUTH-01): dedicated `AdminAuthSession` / `AdminAuthRefreshTokenConsumption` persistence (no polymorphic User/Admin sessions), `POST /api/v1/admin/auth/login`, `GET /admin/auth/me`, Admin refresh/logout/logout-all, ADMIN access-token issuance bound to a real Admin session, namespaced HttpOnly cookies `eggship_admin_at` / `eggship_admin_rt` (`Path=/api/v1/admin`), dummy Argon2id hash timing for unknown emails, Redis/in-process login throttling, `pnpm admin:create` operator bootstrap (no default credentials, no automatic startup), and ADR 0009. CSRF remains a production blocker for cookie-authenticated browser mutations. General Admin account management remains ADM-01.
- Admin identity foundation (ADM-00): `Admin` persistence with canonical unique email, Argon2id `passwordHash`, code-defined `AdminRole`, and `isActive`; `AdminsModule` with `AdminIdentityService`, `AdminRepository`, and `PrismaAdminRoleResolver` wired through `AuthorizationModule.forRoot()`; ADR 0008 documenting email-as-identifier, deferred separate admin sessions (no nullable polymorphic `AuthSession`), and provisional length-oriented password policy. No admin HTTP, no default credentials, no ADMIN access-token issuance, and no automatic bootstrap. PostgreSQL integration covers uniqueness, concurrent same-email create, role resolution, and disabled-admin denial.
- Admin RBAC, permissions, and ownership enforcement (AUTH-08): code-defined `Permission` catalog and `AdminRole` → permission policy (ADR 0007), `AuthorizationService`, `@RequirePermissions` with explicit ALL semantics, reusable `PermissionGuard`, an `AdminRoleResolver` port supplied through `AuthorizationModule.forRoot()`, principal-derived customer ownership scoping with documented BOLA/IDOR rules, stable `AUTH_FORBIDDEN` (403) responses that never disclose the failed policy, and `authz.denied` security logging separate from the future business audit trail. A failing admin directory degrades to a denial with error-level telemetry rather than a server error. Access-token claims are unchanged — no role or permission snapshot — so admin permission changes take effect on the next request.

### Changed

- Authenticated wrong-subject-type principals on customer flows now receive `AUTH_FORBIDDEN` (403) instead of `AUTH_UNAUTHENTICATED` (401), coordinated across `requireCustomerOwnerId` and session logout paths, so browser clients cannot refresh-and-retry into a loop (ADM-00 / ADR 0008).
- Customer authentication completion and current-user profile (AUTH-07): unified `POST /api/v1/auth/complete` (Pattern A — phone-only User create/login from OTP verification grant), `GET /api/v1/auth/me`, allowlisted `PATCH /api/v1/users/me`, consume-first Redis→PostgreSQL handoff (ADR 0006), multi-device sessions, inactive-account rejection, OpenAPI Auth/Users operations, and PG+Redis concurrency integration coverage. Business profile fields deferred pending MIG-01 evidence; CSRF remains a production blocker for cookie-authenticated mutations.
- Public OTP request/verify HTTP APIs (AUTH-06): `POST /api/v1/auth/otp/request` and `POST /api/v1/auth/otp/verify` with enumeration-safe responses, Iranian phone normalization, Redis-backed abuse controls, `Cache-Control: no-store`, `Retry-After` on cooldown/rate-limit errors, short-lived single-use verification grants (no session issuance), OpenAPI `Auth_requestOtp` / `Auth_verifyOtp`, and ADR 0005.
- OTP policy, Redis ephemeral state, and abuse controls (AUTH-05): six-digit CSPRNG OTP, HMAC digests, atomic Redis consume/cooldown/rate-limit Lua scripts, provider-independent `SmsProvider` with development fixed-code adapter and Kavenegar `verify/lookup` adapter (fake-transport unit coverage; live credentials pending), production rejection of the development provider, `OtpService` request/verify primitives without HTTP or session issuance, and Redis OTP integration tests.
- Refresh-session lifecycle and logout (AUTH-04): `POST /api/v1/auth/refresh`, `logout`, and `logout-all` with HttpOnly `eggship_at` / `eggship_rt` cookies, atomic refresh rotation, bounded consumed-digest reuse detection with token-family revocation, cookie/Bearer access-token extraction, `Cache-Control: no-store`, OpenAPI Auth operations, and PostgreSQL concurrency coverage.
- Password hashing and token infrastructure (AUTH-03): Argon2id `PasswordHasher`, HS256 access tokens via `AccessTokenService`, opaque refresh tokens, Bearer `AccessTokenGuard`, typed JWT/TTL config, and Auth domain error mapping at the HTTP boundary.
- User and AuthSession PostgreSQL persistence (AUTH-02): unique canonical Iranian phone identity, multi-device refresh sessions with hashed tokens and token families, conditional rotation/revocation repository primitives, reviewed migration, and real PostgreSQL integration coverage.
- Identity and authentication architecture (AUTH-01): user/store vs admin identity boundaries, cookie/CSRF session strategy, rotating refresh sessions in PostgreSQL, Argon2id password policy, RBAC/ownership separation, ADR 0004, and domain helpers for Iranian phone normalization and refresh-token digests.
- Release automation foundation: SemVer/changelog validation (`pnpm release:check`), human-controlled preparation (`pnpm release:prepare`), release helper tests, and a tag-triggered GitHub Release workflow that does not deploy.
- Opt-in real PostgreSQL/Redis/BullMQ infrastructure integration suite with dedicated `TEST_*` variables, destructive-operation guards, fail-closed runners, and a separate GitHub Actions integration workflow using ephemeral service containers.
- Docker-free local/remote environment workflow policy, documented variable reference, `pnpm env:check`, and test-time `.env` isolation so ordinary suites do not require live PostgreSQL or Redis.
- NestJS OpenAPI foundation with Swagger UI at `/docs`, JSON at `/docs-json`, environment-gated exposure, deterministic `Health_get` documentation, and `pnpm openapi:generate` / `pnpm openapi:check`.
- Cursor, Claude, and Codex project adapters with shared agent workflows, MCP governance policy, and `pnpm check:agent-tooling` drift validation.
- Optional Redis lifecycle and readiness infrastructure with fail-fast configured startup and graceful shutdown.
- BullMQ queue construction, bounded operational defaults, failure reporting, and versioned correlation-aware job context helpers without business queues or workers.
- Redis and queue governance policies plus the accepted Redis/BullMQ architecture decision.
- Provider-independent structured logging with release metadata, centralized sensitive-data redaction, and a Nest-compatible logger adapter.
- Async request/correlation context propagation, validated request IDs, response headers, request-duration logs, and concurrency coverage.
- Safe expected-versus-unexpected error logging integrated with the API exception filter.

### Fixed

- Centralized application HTTP setup so tests exercise the production API prefix, validation, and error filter configuration.
- Sanitized internal error responses and aligned their machine-readable code with the documented API contract.
- Removed local database credentials and defaults from `.env.example`.
