# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Fixed

- Post-validation infrastructure hardening: make PostgreSQL pool limits/timeouts validated and replica-budgeted with a test-only stampede override; scope RR order-create recovery to structured retryable codes plus a proven post-rollback idempotency row; log order creation only after commit; isolate OTP integration cleanup to exact run-owned keys and reject runtime/test Redis target reuse; strengthen migration and OTP-retention governance.
- Native Redis/BullMQ integration (LOCAL-REDIS-01): pad OTP challenge/grant Redis `EXPIRE` by 60s beyond logical expiry so consume can return `expired` before key eviction; reject BullMQ queue names containing `:`; use hyphenated integration queue names; expand Redis/BullMQ real-infrastructure probes (clients, retry/fail retention, custom job ids, key patterns).
- Native PostgreSQL 17 order-create concurrency (LOCAL-PG-01): recover identical/conflicted idempotent creates after REPEATABLE READ + advisory-lock waiters miss the winner without querying an aborted transaction (25P02); raise Prisma/`pg` pool capacity for stampede waiters; map unique violations to idempotency conflicts; remove invalid `CHR(0)` media migration check; fix Inventory SQL/`$executeRaw` advisory-lock and ship-suite expectations exposed on real PG 17.

### Added

- Transactional order creation and idempotency (ORD-03): `OrderCreationService.createOrder` runs price → persist → `reserveForOrder` in one PostgreSQL **REPEATABLE READ** transaction with bounded serialization retry; server-authoritative User/Region snapshots (inactive rejected); PRC-05 pricing snapshot persistence (`grossLineTotal`/`finalLineTotal`, order discount aggregates, applied-discount evidence, `pricingEvaluatedAt`); `(userId, idempotencyKey)` replay/conflict via payload hash + advisory lock; status always `PENDING_REVIEW`; no HTTP. Minimal additive Order/OrderLine migration; unit + PostgreSQL concurrency/integration specs. No payments, returns, or list/detail APIs.
- Public pricing and order snapshot integration (PRC-05): persistence-neutral `OrderPricingService.priceOrderLines` composing PRC-03 LINE then ORDER on the discounted subtotal ([ADR 0015](docs/adr/0015-line-then-order-discount-composition.md)); server-authoritative Product price/name/category with CAT-06 sale visibility; one shared `evaluatedAt`; batch Product/Discount reads (no N+1); REPEATABLE READ snapshot reads with joinable `TransactionContext` for ORD-03; explicit line/order snapshot fields including applied-discount evidence; no Order schema migration (ORD-03 owns persistence); unit + PostgreSQL concurrency/consistency specs; `instructions/pricing.md` / `orders.md` updates. No Order HTTP/create, payments, or promo codes.
- Public catalog APIs closure (CAT-06): confirmed public Category full active list and public Product list/detail visibility (`Product.isActive` + active Category), CAT-01 Product pagination/search(name)/`categoryId`/sort allowlist with unknown-query rejection, empty public Category query DTO so smuggled list params fail closed, safe public DTOs (no Admin lifecycle or inventory), N+1-safe Product queries without nested Category hydration, OpenAPI operation docs, e2e field-minimization coverage, and MIG-01 public-contract deltas in `instructions/catalog.md`. No Product↔Media, inventory authority, personalized pricing, or Redis caching.
- Admin pricing and discount HTTP APIs (PRC-04): `GET/PATCH admin/pricing/products/:productId/price-history|price` with `DISCOUNT_READ`/`DISCOUNT_MANAGE`; paginated append-only price history (newest first, stable `id` tie-break); dedicated price change route via `PricingService` (no-op skip, server-side Admin actor); `GET/POST/PATCH admin/discounts` plus `POST .../activate|deactivate` with CAT-01 list/search/filter/sort, strict DTO validation (no client `isActive` on PATCH), stable discount error codes, OpenAPI, and e2e coverage. Promo-banner API deferred — no evidenced legacy requirements. No schema migration, Order pricing, or public calculation.
- Pricing and discount calculation (PRC-03): pure domain `calculateDiscount` with PERCENT/FIXED integer-Toman math, LINE (`PRODUCT`/`CATEGORY`) and ORDER scopes, server-authoritative targeting from catalog context, UTC eligibility windows, V1 single-winner selection (higher `precedence`, ascending `id` tie-break), floor percent rounding, fixed discount capped at base, bigint-safe bounds, malformed persisted discount skip, and persistence-neutral applied-discount metadata for future Order snapshots; `instructions/pricing.md` calculation section; comprehensive unit tests. No HTTP, DB mutation, promo codes, usage limits, or Redis.
- Discount model and activation lifecycle (PRC-02): Prisma `Discount` with `DiscountType` (`PERCENT`/`FIXED`) and `DiscountTarget` (`ORDER`/`PRODUCT`/`CATEGORY`); integer `percentValue` (1–100) and `fixedAmount` (Toman) with mutual-exclusion CHECKs; optional UTC `startsAt`/`endsAt` window CHECK; explicit `isActive` lifecycle; opaque `precedence` input for later calculation ordering; `ON DELETE RESTRICT` on Product/Category; `PricingModule` / `DiscountService` with server-side validation, activate/deactivate, and admin list support; no HTTP, calculation engine, promo codes, or Order discount snapshots; `instructions/pricing.md` discount section; unit + PostgreSQL integration coverage including DB CHECK enforcement.
- Product price history (PRC-01): append-only Prisma `PriceHistory` (`oldPrice`/`newPrice` int4 Toman with positive/differ CHECKs, `actorType`/`actorId` from authenticated Admin context, `createdAt` timestamptz) with additive migration and `ON DELETE RESTRICT` on Product; `PricingModule` / `PricingService` atomically updates `Product.price` and appends history in one PostgreSQL transaction with row lock, no-op skip, and no history on create; Admin Product PATCH unchanged at HTTP level; no history read API, discounts, or calculation engine; ADR 0010 unchanged; `instructions/pricing.md` and catalog boundary updates; unit + PostgreSQL integration coverage including concurrent chain coherence.
- Admin inventory read/diagnostic APIs (INV-06): paginated `GET /api/v1/admin/inventory` (Product join, name search, `isActive` filter, sort allowlist; no per-row reconciliation), `GET .../:productId/ledger`, `GET .../:productId/reservations` (reservation facts only — no Order PII), and `GET .../:productId/reconciliation` (maps read-only `reconcileProduct`; HTTP 200 when inconsistent; `Cache-Control: no-store` on diagnostics). Existing INV-02 balance/receive/adjust unchanged. `INVENTORY_READ` vs `INVENTORY_ADJUST` split preserved. No repair HTTP, no ledger edit, no Redis.
- Inventory reconciliation (INV-05): internal read-only `InventoryReconciliationService.reconcileProduct(productId)` comparing current balances, ACTIVE reservation aggregates, and append-only ledger reconstruction/lifecycle diagnostics with stable issue codes; PostgreSQL REPEATABLE READ snapshot reads; observability events `inventory.reconciliation.completed` / `inventory.reconciliation.inconsistent`. No HTTP, no auto-repair, no Redis. Admin reconciliation HTTP delivered in INV-06.
- Order transition domain and Inventory orchestration (ORD-02): explicit internal commands `confirmOrder`, `cancelPendingOrderByCustomer`, `cancelOrderByAdmin`, `shipOrder`, and `deliverOrder` with a closed V1 graph, conditional PostgreSQL `UPDATE ... WHERE status = expectedFrom`, idempotent replay that preserves lifecycle timestamps/`deliveryAt`/`cancelReason`, Orders-owned transactions that call `releaseForOrder` / `shipForOrder` only after the Order row wins, canonical Order→Inventory lock order, customer Inventory-error mapping to `ORDER_INVALID_TRANSITION`, and no HTTP/OpenAPI. `DELIVERED → RETURNED`, order creation, and payment remain out of scope.
- Order state machine architecture (ORD-02A): accepted ADR 0014 for V1 transition graph, actor/permission rules, customer cancellation policy, `deliveryAt` semantics, conditional transition concurrency, idempotent replay, Orders↔Inventory transaction orchestration with canonical cross-domain lock order, lifecycle timestamps, inactive-entity behavior, customer BOLA 404 policy, stable Order error codes, and `RETURNED` deferred to ORD-07; durable policy in `instructions/orders.md` and authorization notes in `instructions/authorization.md`. No transition runtime, HTTP, schema changes, or payment state. Transition domain implementation remains ORD-02.
- Order schema and historical snapshots (ORD-01): Prisma `Order` / `OrderLine` with `OrderStatus` enum (`PENDING_REVIEW`, `CONFIRMED`, `SHIPPED`, `DELIVERED`, `CANCELLED`, `RETURNED`); immutable product title/unit price/line total, customer phone, and region name snapshots; integer Toman money (`unitPrice` int4, persisted `lineTotal`/`subtotal`/`total` BIGINT); server-computed totals; `UNIQUE(orderId, productId)`; optional `idempotencyKey` with `UNIQUE(userId, idempotencyKey)`; `OrderRepository` persistence primitives (`createWithLines`, `findById`, `findOwnedById`); no HTTP, no payment models, no Inventory orchestration; ADR 0013; `instructions/orders.md`. Address/profile/discount snapshots deferred pending MIG-01 / profile / PRC tasks. PostgreSQL integration specs exist; live `TEST_DATABASE_URL` run is environment-dependent.
- Inventory ship application contract (INV-04): internal `shipForOrder({ orderId, actor }, tx?)` ships the full ACTIVE reservation set for one order (`onHand -= qty`, `reserved -= qty`, `ACTIVE → SHIPPED`, `SHIP` ledger) in one PostgreSQL transaction with order-scoped advisory serialization, all-or-nothing multi-SKU behavior, all-`SHIPPED` idempotent replay, ship vs release winner semantics, joinable opaque `TransactionContext`, and displayable Persian ship-conflict messages. No ship HTTP, Orders module, partial fulfillment, Redis locks, or returns.
- Inventory reservation and release application contracts (INV-03): `reserveForOrder` / `releaseForOrder` with collapsed multi-SKU lines, all-or-nothing availability inspection, deterministic `productId` locking, `orderId` idempotency (identical replay / mismatched or partial/terminal conflict), order-scoped PostgreSQL advisory serialization, `releaseForOrder` ACTIVE→RELEASED with all-RELEASED replay, joinable opaque `TransactionContext` for future Orders, and displayable Persian shortage/conflict messages. No reservation HTTP, Orders module, SHIP, Redis locks, or reservation TTL.
- Admin inventory warehouse commands (INV-02): `POST /api/v1/admin/inventory/:productId/receive` and `POST /api/v1/admin/inventory/:productId/adjust` (signed delta + required reason) with UUID `Idempotency-Key` replay/conflict semantics, `GET /api/v1/admin/inventory/:productId`, `InventoryCommandIdempotency` persistence, Persian displayable error messages, atomic balance+ledger+idempotency transactions via `AdminInventoryOperationsService`, and `INVENTORY_READ` / `INVENTORY_ADJUST` authorization. - Inventory persistence primitives (INV-01B): `Inventory`, `InventoryReservation`, and append-only `InventoryLedger` with database CHECKs (`onHand`/`reserved` non-negative and `reserved <= onHand`), Product 0/0 backfill and create-time `ensureForProduct`, atomic conditional PostgreSQL quantity updates, reservation ACTIVE→RELEASED/SHIPPED transitions, partial unique order-lifecycle ledger idempotency, and an opaque `TransactionContext` for modular-monolith composition. - Inventory architecture (INV-01A): accepted ADR 0012 for PostgreSQL-authoritative `onHand`/`reserved`, derived `available`, reserve-at-create / ship-at-`SHIPPED` lifecycle, append-only ledger, atomic conditional updates, and Orders↔Inventory contracts; durable policy in `instructions/inventory.md`. - Admin RBAC, permissions, and ownership enforcement (AUTH-08): code-defined `Permission` catalog and `AdminRole` → permission policy (ADR 0007), `AuthorizationService`, `@RequirePermissions` with explicit ALL semantics, reusable `PermissionGuard`, an `AdminRoleResolver` port supplied through `AuthorizationModule.forRoot()`, principal-derived customer ownership scoping with documented BOLA/IDOR rules, stable `AUTH_FORBIDDEN` (403) responses that never disclose the failed policy, and `authz.denied` security logging separate from the future business audit trail. A failing admin directory degrades to a denial with error-level telemetry rather than a server error. Access-token claims are unchanged — no role or permission snapshot — so admin permission changes take effect on the next request.

### Changed

- Customer cancel on ORD-02 now hides non-reservation Inventory `ApplicationError`s (for example `INVENTORY_NOT_FOUND` and `productIds`) as an internal failure instead of returning Inventory codes or details; reservation not-found/conflict still map to `ORDER_INVALID_TRANSITION`.
- Authenticated wrong-subject-type principals on customer flows now receive `AUTH_FORBIDDEN` (403) instead of `AUTH_UNAUTHENTICATED` (401), coordinated across `requireCustomerOwnerId` and session logout paths, so browser clients cannot refresh-and-retry into a loop (ADM-00 / ADR 0008).
- Customer authentication completion and current-user profile (AUTH-07): unified `POST /api/v1/auth/complete` (Pattern A — phone-only User create/login from OTP verification grant), `GET /api/v1/auth/me`, allowlisted `PATCH /api/v1/users/me`, consume-first Redis→PostgreSQL handoff (ADR 0006), multi-device sessions, inactive-account rejection, OpenAPI Auth/Users operations, and PG+Redis concurrency integration coverage. Business profile fields deferred pending MIG-01 evidence; CSRF remains a production blocker for cookie-authenticated mutations.
- Public OTP request/verify HTTP APIs (AUTH-06): `POST /api/v1/auth/otp/request` and `POST /api/v1/auth/otp/verify` with enumeration-safe responses, Iranian phone normalization, Redis-backed abuse controls, `Cache-Control: no-store`, `Retry-After` on cooldown/rate-limit errors, short-lived single-use verification grants (no session issuance), OpenAPI `Auth_requestOtp` / `Auth_verifyOtp`, and ADR 0005.
- OTP policy, Redis ephemeral state, and abuse controls (AUTH-05): six-digit CSPRNG OTP, HMAC digests, atomic Redis consume/cooldown/rate-limit Lua scripts, provider-independent `SmsProvider` with development fixed-code adapter and Kavenegar `verify/lookup` adapter (fake-transport unit coverage; live credentials pending), production rejection of the development provider, `OtpService` request/verify primitives without HTTP or session issuance, and Redis OTP integration tests.
- Refresh-session lifecycle and logout (AUTH-04): `POST /api/v1/auth/refresh`, `logout`, and `logout-all` with HttpOnly `eggship_at` / `eggship_rt` cookies, atomic refresh rotation, bounded consumed-digest reuse detection with token-family revocation, cookie/Bearer access-token extraction, `Cache-Control: no-store`, OpenAPI Auth operations, and PostgreSQL concurrency coverage.
- Password hashing and token infrastructure (AUTH-03): Argon2id `PasswordHasher`, HS256 access tokens via `AccessTokenService`, opaque refresh tokens, Bearer `AccessTokenGuard`, typed JWT/TTL config, and Auth domain error mapping at the HTTP boundary.
- User and AuthSession PostgreSQL persistence (AUTH-02): unique canonical Iranian phone identity, multi-device refresh sessions with hashed tokens and token families, conditional rotation/revocation repository primitives, reviewed migration, and real PostgreSQL integration coverage.
- Identity and authentication architecture (AUTH-01): user/store vs admin identity boundaries, cookie/CSRF session strategy, rotating refresh sessions in PostgreSQL, Argon2id password policy, RBAC/ownership separation, ADR 0004, and domain helpers for Iranian phone normalization and refresh-token digests.
- Release automation foundation: SemVer/changelog validation (`pnpm release:check`), human-controlled preparation (`pnpm release:prepare`), release helper tests, and a tag-triggered GitHub Release workflow that does not deploy.
- Opt-in real PostgreSQL/Redis/BullMQ infrastructure integration suite with dedicated `TEST_*` variables, destructive-operation guards, fail-closed runners, and a separate GitHub Actions integration workflow using ephemeral service containers.
- Docker-free local/remote environment workflow policy, documented variable reference, `pnpm env:check`, and test-time `.env` isolation so ordinary suites do not require live PostgreSQL or Redis.
- NestJS OpenAPI foundation with Swagger UI at `/docs`, JSON at `/docs-json`, environment-gated exposure, deterministic `Health_get` documentation, and `pnpm openapi:generate` / `pnpm openapi:check`.
- Cursor, Claude, and Codex project adapters with shared agent workflows, MCP governance policy, and `pnpm check:agent-tooling` drift validation.
- Optional Redis lifecycle and readiness infrastructure with fail-fast configured startup and graceful shutdown.
- BullMQ queue construction, bounded operational defaults, failure reporting, and versioned correlation-aware job context helpers without business queues or workers.
- Redis and queue governance policies plus the accepted Redis/BullMQ architecture decision.
- Provider-independent structured logging with release metadata, centralized sensitive-data redaction, and a Nest-compatible logger adapter.
- Async request/correlation context propagation, validated request IDs, response headers, request-duration logs, and concurrency coverage.
- Safe expected-versus-unexpected error logging integrated with the API exception filter.
